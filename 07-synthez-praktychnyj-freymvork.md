# Частина 7. Синтез: практичний фреймворк

Це фінал курсу. Усе, що ми **виміряли** на 118 прогонах, згорнуто в один робочий процес: як написати промпт, перевірити його надійність і не наступити на антипатерн. Тримай цю частину поруч під час роботи.

---

## 7.1. Робочий процес написання промпта (5 кроків)

```
1. КОНТЕКСТ   → дай дані+типи, ціль, важливий контекст        (DS1, DS5)
2. ФОРМАТ     → задай форму виводу: схема / якір / закритий набір  (DS4, SE5)
3. ПРИКЛАДИ   → 2–5 few-shot пар, якщо формат критичний        (DS2, SE3)
4. МІРКУВАННЯ → «think step by step», якщо потрібне судження    (DS3, SE4)
5. ВИХІД      → дай «не знаю / немає в контексті», щоб не вигадувало  (SE6, B1)
```

Не кожен промпт потребує всіх 5. Але якщо результат «плаває» — пройдись по кроках і знайди пропущений.

---

## 7.2. Драбина надійності формату (виміряно на Haiku, N=5; два верхні рядки — механіка API, не наш вимір)

Коли вивід має споживатися кодом, обирай **якомога вище**:

| Надійність | Техніка | Приклад |
|:----------:|---------|---------|
| **100%** (гарантує API) | Structured outputs — схема на рівні API (є і на Haiku 4.5) | `output_config.format` |
| **~100%** | Prefill — перший токен (лише Haiku 4.5 і старші; на Claude 4.6+ → 400) | `assistant: {` |
| **~100%** | Якір першого символу | «start with `{`», «start with `def`» |
| **~100%** | Закритий набір міток / fixed sentinel | `MIXED` / `NOT IN DOCUMENT` |
| **~80%** ⚠️ | Негативна заборона | «no markdown» (протікає 1/5) |
| **~80%** ⚠️ | Розмите структурне | «one line», «be brief» |
| **0%** ❌ | Нічого (zero-shot, вільна форма) | «classify this» → 3/3 різних |

**Правило:** для критичних пайплайнів — техніка ~100% **плюс** валідація схемою й повторний прогін на провалі. Не покладайся на заборони.

---

## 7.3. Haiku-специфіка (чому це курс «для Haiku», а не взагалі)

Порівняння з Sonnet 4.6 ([Частина 5](05-rozshyrennya-haiku-vs-sonnet-uk.md)) показало: **промпт-інжиніринг важливіший саме на малій моделі.**

- Sonnet «прощає» слабкий промпт (дав план там, де Haiku відмовився) і дотримується заборон (голий JSON на «no markdown», де Haiku обгорнув).
- Тобто економія на моделі (Haiku — швидша й дешевша) **компенсується якістю промпта**. Те, що Sonnet робить «за замовчуванням», на Haiku треба **прописати явно**.
- Практично: прототипуй логіку на сильнішій моделі, а для прода на Haiku — додай явні приклади, якорі й валідацію.

---

## 7.4. Чотири антипатерни (чого не робити)

| Антипатерн | Симптом на Haiku | Антидот |
|------------|------------------|---------|
| Суперечливі інструкції | мовчки обирає одне, втрата контролю | прибери конфлікт, обери trade-off явно |
| Лише заборони | зміст ок, обсяг/формат протікають | дай **позитивну** ціль («exactly 3 sentences») |
| Перевантаження | усе поверхнево | одна задача = один промпт; решта — ланцюжок |
| Хибна засновка | ризик погодитись | «if any premise is wrong, correct it first» |

## 7.5. Чек-лист «перед тим, як відправити промпт у прод»

- [ ] Чи задано **формат виводу** технікою ≥ ~100% надійності (не лише заборона)?
- [ ] Якщо вивід парситься кодом — чи є **few-shot** або **схема**?
- [ ] Чи дав я моделі **«вихід»** на випадок «немає відповіді» (sentinel)?
- [ ] Чи немає **суперечливих** вимог і **перевантаження** (>1 задача)?
- [ ] Чи **прогнав я промпт N разів** і порахував частку валідних відповідей? *(Одного прогону недостатньо — це головний урок [Частини 6](06-stabilnist-ta-antypaterny.md).)*
- [ ] Якщо текст українською для дисертації — чи є **прохід вичитки** на русизми?

---

## 7.6. Три мета-уроки курсу

1. **Промпт-інжиніринг — вимірюваний.** Не «магічні слова», а інженерія з числами: few-shot дав 1 унікальну відповідь замість 3; якір — 100% проти 80% у заборони.
2. **Перевіряй, не вигадуй.** Кожне твердження тут звірене проти сирого виводу моделі — включно з місцями, де навіть «сильний» промпт спрацював на 80%, а не 100%. Чесний провал цінніший за відполірований приклад.
3. **Контекст моделі має значення.** Те, що велика модель робить сама, малій треба прописати. «Найкраща практика» без прив'язки до моделі — неповна.
