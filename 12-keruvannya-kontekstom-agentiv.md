# Частина 12. Керування контекстом агентів

Контекстне вікно — **не безкоштовний ресурс**, навіть коли воно 1M токенів. Ця частина — про виміряну деградацію («context rot»), чотири стратегії роботи з нею, серверні API-примітиви 2026 і економіку кешування.

> 📚 **Джерела:** Anthropic Engineering (context engineering, multi-agent, harnesses), емпірика — Chroma Context Rot (18 моделей), NoLiMa (ICML 2025), arXiv EMNLP 2025; офіційні API-докси (context editing, compaction, memory tool, prompt caching), докси Claude Code memory, контрапункт Cognition. Зібрано 2026-08-21, кожне твердження реально прочитане за URL.

## 12.1. Context rot — виміряний, а не відчутий

Три незалежні лінії доказів, що **якість падає з ростом входу навіть у межах «підтримуваного» вікна**:

- **Chroma «Context Rot» (2025-07):** 18 фронтирних моделей (Claude Opus/Sonnet/Haiku, GPT-4.1/4o/o3, Gemini 2.5, Qwen3) на контрольованих NIAH-варіантах при **фіксованій складності задачі**: «performance grows increasingly unreliable as input length grows». Найдивніше: **перемішаний/незв'язний** «стіг» давав кращі результати, ніж логічно зв'язний — у всіх 18 моделей; автори чесно кажуть, що пояснення немає.
- **NoLiMa ([arXiv:2502.05167](https://arxiv.org/abs/2502.05167), ICML 2025):** якщо прибрати лексичний збіг між питанням і «голкою» (лишити тільки семантичний), **11 із 13** моделей із заявленими 128K+ падають нижче 50% свого short-context бейзлайну вже на **32K**; GPT-4o: 99.3% → 69.7%. Reasoning-моделі теж деградують — «більше міркувань» цього не лікує.
- **EMNLP 2025 Findings ([arXiv:2510.05381](https://arxiv.org/abs/2510.05381)):** падіння 13.9–85% зі зростанням довжини **навіть коли нерелевантні токени замінені пробілами/замасковані** — тобто це не (лише) провал retrieval. Часткова милиця: «процитуй знайдені докази перед відповіддю» (+до 4% на RULER).

> ⚠️ **Чесна межа даних:** ці студії — на моделях 2025 року; реплікації на Sonnet 5/Opus 5/Fable 5 ми не знайшли. Наскільки нове покоління помʼякшило context rot — відкрите питання (так і кажемо, а не вгадуємо).

**Правило 12.1.** Довге вікно ≠ дозвіл наливати все. Кожен токен у вікні має **заробити своє місце**.

## 12.2. Чотири стратегії (канон Anthropic Engineering, 2025-09-29)

1. **Just-in-time retrieval** — тримай у контексті **легкі посилання** (шляхи файлів, ID, запити), а вміст підтягуй інструментами в момент потреби; не преднавантажуй усе. Так працює Claude Code.
2. **Compaction** — біля межі вікна: підсумувати й реініціалізуватись, зберігаючи **архітектурні рішення і невирішені баги**, а не сирі виводи інструментів.
3. **Структуровані нотатки / памʼять** — знання живуть **поза вікном** у файлах і повертаються на вимогу (Anthropic демонструвала Claude, що грає в Pokémon тисячі кроків, ведучи карти і стратегію в нотатках).
4. **Архітектури з підагентами** — брудна підзадача йде в **чисте вікно** окремого агента, назад повертається дистилят на 1–2k токенів. (Контрапункт Cognition — див. [Частину 11](11-multyagentna-rozrobka.md): для звʼязного кодингу ізоляція ріже спільні рішення.)

## 12.3. 2026: це вже примітиви API, а не хаки промпта

Найважливіший зсув року: керування контекстом **переїхало на сервер**.

| Примітив | Що робить |
|---|---|
| **Context editing** (`clear_tool_uses_20250919`) | Автоматично чистить найстаріші tool-результати (конфігуровані trigger / keep / clear_at_least / exclude_tools) — до того, як промпт дійде до моделі |
| `clear_thinking_20251015` | Робить те саме зі старими thinking-блоками (скільки лишати — параметр `keep`) |
| **Server-side compaction** (`compact_20260112`, бета 01.2026) | Сам підсумовує стару історію в compaction-блок після порога (дефолт 150K); клієнт зобовʼязаний передавати блок назад; сумаризація сама коштує токени і білиться поітераційно |
| **Memory tool** (`memory_20250818`) | Персистентна директорія `/memories` (view/create/str_replace/…), що переживає вікна; офіційна рекомендація — **у парі** з compaction: компакція тримає вікно малим, памʼять зберігає те, що мусить пережити сумаризацію |

Практичний патерн «multisession development» (докси + harness-пост 2025-11-26): initializer-сесія створює progress-лог + чекліст функцій + init-скрипт; кожна наступна сесія **читає й оновлює лог** перед завершенням; git — механізм відновлення. Це той самий патерн «зміни інженерів» із [Частини 10](10-avtomatyzovana-rozrobka-z-shi.md).

## 12.4. Структуровані нотатки в реальному інструменті

Докси Claude Code (v2.1.2xx) — жива реалізація «нотаток» двох сортів:
- **CLAUDE.md** — пише людина; ієрархія scope'ів (managed/user/project/local), рекомендовано до 200 рядків на файл; **переживає `/compact`** (перечитується з диска) — на відміну від інструкцій, сказаних просто в розмові.
- **Auto memory** — пише сам Claude: `~/.claude/projects/<project>/memory/` з категоріями (user/feedback/project/reference) та індексом MEMORY.md (стеля 200 рядків / 25KB), який вантажиться щосесії; тіла тем — на вимогу (той самий just-in-time).

> Цей курс створено з тим самим механізмом: правило «валідувати, а не вигадувати» зберігалося в auto memory між сесіями.

## 12.5. Економіка кешу: чому порядок у промпті = гроші

Офіційні докси prompt caching: читання кешу — **0.1×** базової ціни входу (на Fable 5.1 і Mythos 5.1 — 0.025×); запис — 1.25× (5 хв TTL) або 2× (1 год). Але хіт вимагає **байт-у-байт ідентичного префікса** до breakpoint: один timestamp чи UUID на початку системного промпта = **тихі 100% промахів**. Змінені визначення інструментів інвалідовують весь ланцюг (tools → system → messages). Тому context-editing спроєктований обережно щодо кешу (`clear_at_least` існує саме щоб перезапис кешу окупався).

**Правило 12.5.** Стабільне — наперед (системний промпт, інструменти), змінне — в кінець. Це не стилістика, це **10× різниці в ціні** входу.

## 12.6. Правила частини (зведення)

1. Кожен токен має заробити місце: релевантність > повнота (context rot виміряний трьома незалежними студіями).
2. Посилання в контексті, вміст — за вимогою (JIT).
3. Компакція — для розміру вікна; **файлова памʼять — для істини**, що мусить пережити компакцію; використовуй разом.
4. Брудні підзадачі — в чисті вікна підагентів, назад — дистилят (з поправкою Cognition для звʼязного кодингу).
5. Стабільний префікс = 10× дешевший вхід; volatile-контент нижче breakpoint.
6. Для довгих робіт: progress-лог + git як зовнішня памʼять «змін».

## Вправи (Частина 12)

1. **12-A.** Агент на 300-му ході погіршився: плутає давні рішення, «забуває» вимоги. Назви три механізми з цієї частини, які треба було закласти з початку.
2. **12-B.** У системному промпті колеги перший рядок — `Сьогодні: {datetime.now()}`. Чому це дорого і як виправити?
3. **12-C.** Чим відрізняються compaction і memory tool, і чому офіційна порада — використовувати їх **разом**?

### Відповіді
1. **12-A.** (1) Context editing / компакція, щоб старі tool-результати не витісняли важливе; (2) файловий progress-лог + нотатки рішень (переживають компакцію/ресети — патерн initializer→sessions); (3) підагенти для брудних підзадач, щоб сміття не потрапляло в головне вікно взагалі.
2. **12-B.** Динамічний перший рядок ламає байт-ідентичність префікса → 0% кеш-хітів → вхід коштує ~10× дорожче можливого. Виправлення: волатильне (дату, ID) — **після** cache-breakpoint (в кінець системного промпта або в перше повідомлення), стабільне ядро — наперед.
3. **12-C.** Compaction стискає **вікно** (сумаризує історію, щоб влізти далі), але сумарізація може загубити деталі; memory tool зберігає **факти поза вікном** назавжди і повертає на вимогу. Разом: компакція тримає розмір, памʼять — гарантує, що критичне (рішення, невирішені баги, стан функцій) переживе будь-яку сумаризацію чи ресет.

---

> **Підсумок Частини 12.** У 2026 контекст — це **бюджет, що деградує**: виміряно на 18 моделях. Дисципліна: JIT-посилання замість преднавантаження, компакція для розміру, файли для істини, чисті вікна для бруду, стабільний префікс для економіки. І чесна прогалина: наскільки нове покоління моделей помʼякшило context rot — ще ніхто не переміряв.
